# User Interface

> **For Claude:** read `01-architecture.md` §7 (client structure) and `02-conventions.md` §12
> first. `theme.ts` belongs in `packages/contracts/src/content/` and `views.ts` in
> `packages/contracts/src/`; both were typechecked. The six built-in themes in
> `spec/fixtures/library/themes/` passed the contrast checker in §3.2, and every font named here
> was confirmed on npm under the SIL Open Font License.

The interface exists to serve a story. Reading comes first; every control is close at
hand but quiet until wanted. Each campaign can look like its genre, and the app works
equally well on a desktop and a phone.

## 1. Principles

- **The story leads.** Narration is the largest, calmest thing on screen. Controls appear
  on hover, focus, or a tap, and step back after.
- **Mechanics are one line until you want more.** A roll shows as a single readable line
  in the story; tapping it opens the full dice card.
- **Everything is editable from where you see it.** Every output carries its own controls
  for edit, regenerate, versions, fork, and X (CSET-022), in the same place every time.
- **Each campaign has its own look; the app has one shape.** Themes change color, type,
  and ornament. Layout, components, and behavior never change between themes.
- **Desktop and phone are equals.** Every screen is designed for both, and both are
  tested (§13).

## 2. Screens and routes

| Route | Screen | Purpose |
|---|---|---|
| `/` | Library | Campaigns, with continue, new, import, and export |
| `/new` | New campaign | The creation wizard (§8.2) |
| `/c/:campaignId` | Play | The story, input, and side panels (§5–7) |
| `/c/:campaignId/journal/:entityId?` | Journal | The PC's knowledge (`10-journal.md`) |
| `/c/:campaignId/timeline` | Timeline | Branches and bookmarks (§8.4) |
| `/c/:campaignId/inspector/:turnId` | Inspector | Every model call of a turn (§9) |

- **UI-001** Routes are the only navigation state; refreshing any screen restores it.
  Opening a campaign goes to its current branch (TRN-101).

## 3. Themes

### 3.1 Theme definitions — `theme.ts`

A theme is a content definition (`theme.<slug>`), resolved like the others (SCH-010):
pack, then user library, then built-in library. Tone profiles name one with `themeId`.

```ts
import { z } from 'zod';
import { ContentSchemaVersionSchema, SlugSchema, ThemeIdSchema } from './common';

/*
 * A theme is a campaign's look (14-ui §3): colors, type, and a few ornaments. Themes
 * change tokens only; layout and components are the same in every theme.
 */

const HexSchema = z.string().regex(/^#[0-9a-fA-F]{6}$/);

/** Every color a theme must define. Contrast rules are checked by `themeIssues` (UI-031). */
export const PaletteSchema = z.strictObject({
  background: HexSchema, // the page
  surface: HexSchema, // panels, cards, the input dock
  text: HexSchema, // narration and primary text
  textMuted: HexSchema, // secondary text: timestamps, roll lines, hints
  playerText: HexSchema, // the player's own input in the story
  accent: HexSchema, // primary actions, focus rings, links
  onAccent: HexSchema, // text on accent-colored buttons
  border: HexSchema, // dividers and outlines
  positive: HexSchema, // success, healing
  caution: HexSchema, // partial results, stale stages, GM mode frame
  negative: HexSchema, // failure, harm, errors
});
export type Palette = z.infer<typeof PaletteSchema>;

/** A bundled font (UI-034) or a font file shipped in the pack's `fonts/` folder. */
export const FontRefSchema = z.strictObject({
  family: SlugSchema, // e.g. "spectral"; resolved against the font registry
  weight: z.int().min(100).max(900).default(400),
  italicForEmphasis: z.boolean().default(true),
});

export const ThemeSchema = z.strictObject({
  schemaVersion: ContentSchemaVersionSchema,
  id: ThemeIdSchema,
  name: z.string().min(1).max(80),
  description: z.string().max(300),
  /** At least one. With both, the device's light/dark preference picks (UI-033). */
  palettes: z.strictObject({ dark: PaletteSchema.optional(), light: PaletteSchema.optional() }),
  fonts: z.strictObject({
    narration: FontRefSchema, // the story
    interface: FontRefSchema, // controls, panels, labels
    display: FontRefSchema.optional(), // scene and place headings; defaults to narration
    mechanics: FontRefSchema.optional(), // dice cards and numbers; defaults to interface
  }),
  narration: z.strictObject({
    size: z.enum(['small', 'medium', 'large']).default('medium'), // 17, 19, 21 px base
    lineHeight: z.number().min(1.3).max(2).default(1.6),
    measure: z.int().min(45).max(80).default(66), // characters per line, at most
  }),
  shape: z.strictObject({ radius: z.int().min(0).max(16).default(6) }),
  ornament: z.strictObject({
    sceneBreak: z.string().max(12).default('*'), // shown between scenes
    dropCap: z.boolean().default(false), // first letter of each scene's opening narration
    texture: z.enum(['none', 'grain', 'paper', 'scanlines']).default('none'), // CSS-generated, no images
  }),
});
export type Theme = z.infer<typeof ThemeSchema>;

/** Bundled fonts: SIL Open Font License faces shipped with the app (UI-034). */
export const BUNDLED_FONTS = [
  'atkinson-hyperlegible',
  'spectral',
  'alegreya-sans',
  'gentium-book-plus',
  'figtree',
  'ibm-plex-sans',
  'ibm-plex-mono',
  'crimson-pro',
  'im-fell-english',
  'literata',
] as const;
```

### 3.2 Rules

- **UI-030** **Which theme applies,** highest priority first: the device's reader
  preference if it forces one (§12.2); the campaign's override (campaign settings);
  the tone profile's `themeId`; the house theme. Screens outside a campaign use the
  house theme unless the device forces another.
- **UI-031** **Readable by construction.** `themeIssues` checks every palette: text,
  muted text, and player text at 4.5:1 or better against their backgrounds (WCAG AA);
  text on accent at 4.5:1; accent and the three result colors at 3:1 against surfaces
  (UI components); player text different from narration text; every font known. A theme
  with issues is listed with its issues and cannot be applied.
- **UI-032** Themes become CSS custom properties on the document root (`--color-text`,
  `--font-narration`, `--radius`, …). Tailwind's theme reads those variables, so
  components never name a color or font directly. Switching themes changes the
  variables only.
- **UI-033** A theme with both palettes follows the device's light or dark preference;
  with one, it uses that one everywhere.
- **UI-034** **Fonts are bundled.** The app runs offline on a LAN, so fonts ship with it
  as the `@fontsource` packages for the faces in `BUNDLED_FONTS`. A pack may add fonts as
  `.woff2` files in a `fonts/` folder with their license file; the pack loader rejects a
  font without a license file.
- **UI-035** Textures are generated in CSS (gradients or an inline SVG filter), never
  image files, and are disabled when the device prefers reduced transparency or the
  high-contrast theme is active.
- **UI-036** Ornaments: `sceneBreak` is shown centered between scenes in the story;
  `dropCap` sets the first letter of each scene's opening narration in the display face.

- **UI-040** The story column is left-aligned text, never justified, at most the
  theme's `measure` in characters wide, centered in its area.
- **UI-041** The side panel is 340–420 px wide on desktop and resizable; its width and
  last tab are remembered per device.
- **UI-042** No screen scrolls horizontally at any width from 360 px up. Tables (the
  inspector, the chronicle) become stacked rows on phones.
- **UI-043** The input dock stays above the on-screen keyboard on phones, and the story
  keeps its scroll position when the keyboard opens.

## 5. The story

### 5.1 Turns

Each turn renders, in order: the player's input; the compact roll line or OOC exchange;
the narration; and any after-turn cards (off-screen news, failures).

- **UI-050** The player's input is set in the narration face, in `playerText` color and
  indented, so the player's words are distinct without a speech-bubble metaphor. OOC
  input and OOC replies are set in the interface face, muted, and marked "Out of
  character".
- **UI-051** Narration is set in the narration face at the theme's size and line height.
  Voiced lines (CTX-066) are part of the narration text; nothing marks which calls
  produced them outside the inspector.
- **UI-052** A scene break shows the theme's `sceneBreak` ornament, then the new scene's
  place and date in the display face.
- **UI-053** Streaming narration appears as it arrives. The view follows new text only
  if the reader is already at the bottom; otherwise a "New text below" button appears.
  With reduced motion, streamed text appears a sentence at a time.
- **UI-054** Turn status shows as one quiet line under the turn while work is underway:
  "The GM is considering…", "Writing…", "Remembering…" (extraction), "The world moves…"
  (world ticks, with progress for skips). Background states never block reading.
- **UI-135** While narration streams, the input dock's send button becomes **Stop**,
  which cancels the narration and keeps what was written (TRN-149).

### 5.2 Mechanics: compact, expandable

- **UI-055** A resolved roll shows as one line: the stat's name, the number of dice (or
  the total, for sum methods), and the result's label, followed by any harm taken, e.g.
  *"Strength, 3 dice: partial. Wrenched Wrist (lesser)."* A direct ruling with
  consequences shows them the same way, without dice. Tapping or pressing Enter on the
  line expands the **dice card** in place.
- **UI-056** The dice card shows: the points breakdown with every labeled modifier
  (RUL-026); the dice, with kept dice emphasized; the result; effect and its modifiers;
  each stakes tier, with the applied one marked; every harm result step by step (armor,
  resistance, placement); clock changes; time passed; and the GM's explanation at the
  allowed level (TRN-081), collapsed by default.
- **UI-057** **Awaiting resolution.** When a draft needs a response (TRN-043), the
  compact line becomes a short card at the end of the story: the result, the
  consequences that will apply, and **Accept** as the primary action, with **Change**
  (opens the full card's controls: reroll, set outcome, edit consequences) and
  **Cancel turn**. The input dock is disabled with the reason "Accept or change the roll
  first". Deaths and survived fatal harm are stated plainly on the card (RUL-122).
- **UI-058** A device preference shows dice cards expanded by default.

### 5.3 States and recovery

- **UI-059** Stale stages, failed stages, extraction or world-tick failures, and replay
  conflicts show as a small badge on the turn in the `caution` or `negative` color, with
  a plain sentence and its fix: "Memories weren't saved for this turn. Retry, or retry
  with another model." Badges never stack more than one per turn; the turn menu lists
  them all.
- **UI-060** After a skip, a "While time passed" card lists the off-screen news
  (TIME-100), each item with its date.
- **UI-061** When the PC dies (RUL-121), the story ends with the death narration and a
  card offering **Rewind** and **Edit this turn**. The input dock offers OOC only.

## 6. Turn actions

- **UI-062** Every turn has a menu, opened by a quiet "…" button that appears on hover
  or focus (desktop) and is always visible on touch, or by long-press on the turn
  (phone, as a bottom sheet). Actions: Edit (input, ruling, roll, narration), Regenerate,
  Regenerate with instruction, Regenerate with another model, Versions, Fork from here,
  Bookmark, X, Inspect.
- **UI-063** **History mode.** Editing a turn that isn't the head opens a choice, with
  the player's last choice preselected (TRN-090): **Rewrite** ("Discard everything after
  this turn and continue from here. The discarded turns are kept on an archived
  branch.") or **Retcon** ("Keep everything after this turn. What happened later is
  replayed on top of your change, and anything that no longer fits is flagged.").
- **UI-064** When a turn is shared with another branch (TRN-110), edit actions say so:
  "This turn is also on *Sided with the Wardens*. Editing makes a copy for this branch."
- **UI-065** **Versions** lists a stage's versions newest first with a short preview;
  choosing one restores it (TRN-116). Stale stages offer **Regenerate** and **Keep as
  is** (§7.1 of the turn engine).
- **UI-066** **X** (CSET-022) is in every turn menu and on journal entries.

## 7. Input and panels

### 7.1 The input dock

- **UI-070** A mode switch chooses **In character** or **Out of character**. OOC mode
  changes the dock's placeholder ("Ask the GM…") and outline color, so the mode is
  never ambiguous. Tab toggles the mode from the keyboard.
- **UI-071** When suggestions are enabled (TRN-059), they appear as up to six short
  options above the dock; choosing one fills the input for the player to send or edit.
- **UI-072** **Skip** opens the skip control (TIME-040): until a time of day (from the
  calendar's list), for a duration, or until a date, with an optional activity.
- **UI-073** When input is unavailable, the dock says why and how long: "The world
  moves… (period 2 of 5)". The draft text is kept, per campaign, on this device.
- **UI-074** Enter sends on desktop; Shift+Enter adds a line. On phones the send button
  sends and Enter adds a line.

### 7.2 Side panels

The side panel (desktop) or sheets (phone, tablet) have three tabs.

- **UI-080** **Character:** the PC's `CharacterSheet` (§11): stats; harm as one row per
  level with empty slots shown up to capacity; conditions and permanent statuses; gear
  by slot and layer with concealed items marked "hidden from others", containers
  expandable with their space used, held items, and load when encumbrance is on. Gear
  can be managed here directly or "in the story" (GEAR-080, GEAR-081).
- **UI-081** **Scene:** the `SceneView`: place, date and time of day, who is present by
  display name with their appearance, and visible clocks drawn as segmented circles.
- **UI-082** **Journal:** search, the people and places present, and recent entries,
  linking to the full journal.

## 8. Other screens

### 8.1 Library

- **UI-083** Campaigns as a list (phone) or grid (desktop), most recent first, each
  showing its name, setting, current date in game, last played, a swatch of its theme,
  and its content settings summary (CSET-023). Continue is the primary action. Packs
  with errors are listed with their errors (SCH-102).

### 8.2 New campaign

- **UI-084** A wizard, one step per screen on phones and a stepped single page on
  desktop: pack and scenario; tone profile; ruleset (with stat conversion when needed,
  SCH-114); content settings (CSET); the PC (premade or created, with stat points
  enforced by the ruleset and the remaining points shown); theme (preselected from the
  tone profile, with a live preview of narration in that theme); review. Review warns
  about unassigned model roles and links to settings.

### 8.3 Journal

- **UI-085** As `10-journal.md` §10 describes: an index by kind, entity pages,
  chronicle, claims, and search. Notes are labeled "Private: never sent to the GM";
  beliefs are labeled "The GM sees these".

### 8.4 Timeline

- **UI-086** The branch tree as a vertical list of branches, each showing where it forked
  and its latest turn; archived branches behind a "Show archived" switch. Selecting a
  turn shows its narration preview with Fork, Switch to branch, Bookmark, and Rewind.

### 8.5 Campaign settings

- **UI-087** Content settings (with history, CSET-020), theme (any valid theme, with live
  preview), template overrides (a list of overridable templates; editing opens a text
  editor with a "Preview against this campaign" pane, CTX-008), and the explanation
  level.

### 8.6 Settings

- **UI-088** Machine config, edited through the API (PRV-003): providers with a health
  dot each (PRV-091); model profiles with **Probe** (PRV-090) and its results; role
  assignments, including explicit-content routing; the `context`, `world`, and `memory`
  sections under "Advanced", with every field's default shown; PIN; data folder. Fields
  that need a restart say so.

## 9. Inspector

- **UI-090** For one turn: every model call (role, model, duration, tokens in and out,
  outcome). Choosing a call shows tabs: **Prompt** (each tier as a section with its
  budget bar, estimated tokens, and what was trimmed; cached-prefix tiers marked),
  **Memories** (each retrieved memory with knower, reason, and score parts, MEM-078),
  **Output** (raw output, thinking if any, parsed output, and every attempt with its
  issues), and **Templates** (files used and their layers).
- **UI-091** Copied turns show their original's records (TRN-113). The inspector is
  read-only, except "Open in preview", which renders the same templates against the
  current campaign.

## 10. GM mode

- **UI-092** GM mode is a per-device toggle, off by default, in the campaign menu. The
  first time on a device it confirms: "GM mode shows hidden truth, including secrets,
  lies, and what other characters think. Turn it on?"
- **UI-093** While it is on, a 3 px frame in the theme's `caution` color surrounds the
  viewport and the top bar says "GM mode", so spoilers are never visible by accident.
- **UI-094** Requests made in GM mode ask for GM data; turning it off removes every
  GM-only response from the client cache at once.
- **UI-095** GM mode adds: full rulings and explanations; GM clocks; "View as" in the
  journal (JRN-050); NPC feelings toward the PC; claims marked true or false; world-tick
  summaries per turn; and truth editing (MEM-120).

## 11. Panel contracts — `views.ts`

```ts
import { z } from 'zod';
import { EntityIdSchema, IdSchema } from './primitives';
import { ClockIdSchema, HarmLevelSchema, StatIdSchema, StatusTagSchema } from './rules';

/*
 * Read models for the play screen's panels (14-ui §6). Always from the PC's point of view:
 * display names (JRN-020), visible appearance (GEAR-060), and visible clocks only, unless
 * the request is made in GM mode.
 */

export const PresentCharacterSchema = z.object({
  entityId: EntityIdSchema,
  displayName: z.string(),
  appearance: z.string(), // GEAR-062
  isPc: z.boolean(),
});

export const ClockViewSchema = z.object({
  id: ClockIdSchema,
  name: z.string(),
  segments: z.int(),
  filled: z.int(),
  completed: z.boolean(),
  hidden: z.boolean(), // a GM clock; present only in GM mode
});

export const SceneViewSchema = z.object({
  sceneId: IdSchema,
  placeId: EntityIdSchema,
  placeName: z.string(),
  gameTimeLabel: z.string(),
  timeOfDay: z.string(),
  present: z.array(PresentCharacterSchema), // in order of joining the scene (CTX-012)
  clocks: z.array(ClockViewSchema),
  timeUntil: z.array(z.object({ name: z.string(), minutes: z.int().positive() })), // TIME-021
});
export type SceneView = z.infer<typeof SceneViewSchema>;

export const StatusViewSchema = z.object({
  id: IdSchema,
  name: z.string(),
  tags: z.array(StatusTagSchema),
  treated: z.boolean(),
  permanent: z.boolean(),
  healsIn: z.string().nullable(), // e.g. "about 2 days"; null if it will not heal on its own
});

export type ItemView = {
  entityId: string;
  name: string;
  quantity: number;
  concealed: boolean; // GEAR-030: hidden from others
  container: { capacity: number; used: number; items: ItemView[] } | null;
};
export const ItemViewSchema: z.ZodType<ItemView> = z.lazy(() =>
  z.object({
    entityId: EntityIdSchema,
    name: z.string(),
    quantity: z.int().positive(),
    concealed: z.boolean(),
    container: z
      .object({ capacity: z.int(), used: z.int(), items: z.array(ItemViewSchema) })
      .nullable(),
  }),
);

export const CharacterSheetSchema = z.object({
  entityId: EntityIdSchema,
  displayName: z.string(),
  stats: z.array(
    z.object({ id: StatIdSchema, name: z.string(), abbreviation: z.string(), rating: z.int() }),
  ),
  /** One row per ruleset harm level, least severe first, with capacity for empty slots. */
  harm: z.array(
    z.object({
      level: HarmLevelSchema,
      levelName: z.string(),
      capacity: z.int().nullable(),
      statuses: z.array(StatusViewSchema),
    }),
  ),
  conditions: z.array(StatusViewSchema), // non-harm statuses
  permanent: z.array(StatusViewSchema), // lasting conditions (RUL-104)
  gear: z.object({
    slots: z.array(
      z.object({
        slotId: z.string(),
        name: z.string(),
        covered: z.boolean(), // hidden by another worn item (GEAR-003)
        layers: z.array(
          z.object({
            name: z.string(),
            visibility: z.enum(['visible', 'concealed']),
            items: z.array(ItemViewSchema),
          }),
        ),
      }),
    ),
    held: z.array(ItemViewSchema),
    carried: z.array(ItemViewSchema), // encumbrance mode only
    load: z.object({ load: z.number(), capacity: z.number() }).nullable(),
  }),
});
export type CharacterSheet = z.infer<typeof CharacterSheetSchema>;
```

|---|---|
| `GET /api/campaigns/:campaignId/scene?branchId=` | `SceneView` |
| `GET /api/campaigns/:campaignId/characters/:entityId/sheet?branchId=` | `CharacterSheet` (the PC; any character in GM mode) |

## 12. Client behavior

### 12.1 Data

- **UI-100** Server state lives in TanStack Query (ARCH-120), keyed by campaign and
  branch: `['turns', campaignId, branchId]`, `['turn', campaignId, turnId]`,
  `['scene', campaignId, branchId]`, `['sheet', campaignId, entityId]`,
  `['journal', campaignId, …]`, and so on. GM-mode responses add `'gm'` to the key.
- **UI-101** One SSE connection per open campaign. Events update the cache:
  `narration.delta` writes its text at `offset` in the turn's narration, so text the
  client already has from fetching the turn mid-stream is not repeated, and an offset
  past the end of the cached text refetches the turn; `turn.status` and
  `resolution.ready` update the turn; `narration.done` refetches it; `error` refetches
  its turn, or shows the error in plain words when it names no turn (UI-122);
  `turn.created` and `branch.changed` refetch the branch's turns and the campaign;
  `state.changed` invalidates the scene, the affected entities' sheets, and the
  journal; `job.updated` changes nothing until a phase shows job progress;
  `resync.required` refetches everything for the campaign (ARCH-091).
- **UI-102** Commands are mutations that never update the cache optimistically; the
  server's events are the source of truth. A `conflict` (TRN-120) refetches and tells
  the player "This campaign changed on another device. Showing the latest."

### 12.2 Per-device preferences

- **UI-103** Stored in `localStorage` (every read and write guarded, falling back to
  defaults): text size (five steps around the theme's size), line spacing, theme
  override (campaign, house, or high contrast), light or dark (auto, light, dark),
  reduced motion (system or on), dice cards expanded, panel width and tab, input drafts,
  the last history mode, and GM mode.

## 13. Accessibility and motion

- **UI-110** Every control is reachable and operable by keyboard, with a visible focus
  ring in the theme's accent (CONV-103). Touch targets are at least 44 × 44 px.

## Traps

- **Each named event needs its own listener (UI-101).** The server names every frame by
  its payload type (`event: turn.status`), and an `EventSource` delivers a named frame
  only to a listener for that name, never to `onmessage`. `campaign-events.ts` registers
  one listener per type from a table typed
  `satisfies Record<ServerEventPayload['type'], true>`, so a new payload type does not
  compile until it is listed.
- **The `error` payload shares its name with the connection's error (UI-101).** A
  listener for `error` hears both the server's `error` frames, which are `MessageEvent`s
  with data, and `EventSource`'s own connection errors, which are plain `Event`s. Check
  which it is before parsing.
- **With `EventSource`, resuming from the last event ID is the browser's job (UI-132,
  ARCH-091).** The browser resends `Last-Event-ID` when it reconnects a dropped stream,
  and code cannot set that header. When the browser gives up instead, after an error
  status such as `auth_required`, the client opens a new `EventSource`, which starts
  from nothing: so once it opens, the client refetches the campaign. The tests' fake
  `EventSource` has `drop` for the browser's own reconnect and `fail` for giving up.
- **A fetch can overwrite deltas that arrived while it was in flight (UI-101, UI-132).**
  A turn fetched mid-stream holds the narration as of the server's answer (TRN-150).
  Deltas written to the cache before that answer lands are lost when it replaces the
  cached turn, so the next delta's offset is past the end. That gap refetches the turn,
  and `narration.done` refetches it once more at the end. Neither refetch is redundant.
- **Cached settings can send the player back to Settings (PRV-001).** The settings query
  can hold a config fetched before the player saved their first model profile, and
  TanStack Query shows cached data at once while it refetches. So the library acts only on
  settings fetched since it opened (`isFetchedAfterMount`); acting on `isSuccess` would
  send a player who has just set up a model straight back to `/settings`. A save through
  `PUT /settings` should invalidate `['settings']` too.
- **A card's last-played words differ between devices (UI-083).** The library formats
  `lastPlayedAt` in the device's locale and time zone (`Intl.DateTimeFormat(undefined,
  …)`), so the words differ between machines and CI. Tests read the `<time>` element's
  `dateTime`, never its words.
